Overview

The talk frames long-running agents as a combined model problem and systems problem. Andrew walks through the release history from early Claude Code to Agent SDK, Skills, Agent Teams, server-side compaction, and larger context windows. Ash then focuses on more experimental harnesses, especially generator-evaluator loops that separate building from judging and push the evaluator to inspect real outputs rather than trust the generator's internal story.

Key takeaway: better base models extend the frontier, but they do not eliminate the need for harness design. The bottleneck moves from raw capability toward memory, planning discipline, and trustworthy verification.

Why Long Runs Break

Failure area What the speakers mean Why the harness helps
Context Finite windows create amnesia between sessions and "context rot" within a long session. Fresh sessions, compaction, memory files, and progressive disclosure reduce overload.
Planning Models try to do too much in one pass, stop halfway, or exhaust context before finishing. Initializer steps, explicit feature lists, and one-feature-at-a-time loops create smaller units of work.
Verification Models are often satisfied by plausible-looking output, even when the backend or behavior is incomplete. Separate evaluators, live-page testing, and adversarial critique make false completion harder.

Release Arc

The historical portion of the talk argues that long-run performance improved through repeated model-plus-harness co-releases, not model gains alone.

Two numerical claims anchor the story. First, they cite a jump from roughly one hour to roughly twelve hours on a minimal-scaffold benchmark over about a year of model progress. Second, they mention practical greenfield app builds that now often land in the three-to-five-hour range rather than requiring thirty-hour runs.

Harness Patterns That Matter

1. Fresh context plus persistent artifacts

The long-running app-builder example starts with an initializer that writes durable state: a feature list, a progress file, a repo bootstrap, and an init script. From there, each loop begins in a fresh context window, regains its bearings from the filesystem, smoke-tests the project, picks exactly one unfinished feature, implements it, verifies it, commits it, and updates the persistent state.

initializer
  -> featurelist.json
  -> progress.json
  -> init script
loop
  -> fresh session regains bearings
  -> smoke test / start app
  -> pick one unfinished feature
  -> implement
  -> verify with live checks
  -> commit + mark pass
  -> continue until complete

2. Generator-evaluator separation

A single session checking its own work is easy to fool. Their stronger pattern splits the builder from the judge. The evaluator does not just read diffs; it uses tools like Playwright to inspect the live page, click around, and return critique grounded in behavior. The generator then has to repair the issue without inheriting the evaluator's entire internal chain of thought.

3. Role specialization by model cost and capability

One practical combination they call out is using the strongest model for planning and a cheaper or faster model as the workhorse. They describe Opus-class models as especially strong for planning and tool choice, while Sonnet-class models become economical executors.

4. Breadcrumbs for future agents and humans

A recurring theme is writing structured state back to disk. JSON files are preferred because the model is less likely to casually overwrite them. These files act as breadcrumbs for another agent or a human to inspect and continue from, including records like what was tried, what the evaluator found, and what fixes actually worked.

5. Greenfield is easier than brownfield

The speakers are explicit that this pattern currently fits greenfield builds better than existing production codebases. Brownfield use still benefits from agents, but usually through narrower loops such as monitoring, bug-fix generation, pull-request creation, or targeted evaluator passes rather than one giant autonomous app-building run.
